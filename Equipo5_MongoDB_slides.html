01 · El problema

Cuando la fila no es la forma

MySQL · tabla productos

MongoDB · colección productos

  talla: "M" }

  voltaje: "127 V" }
{ nombre: "Libro", precio: 320,
  paginas: 280 }

Esquema fijo

6 de 15 celdas vacías. Cada tipo nuevo de producto agrega una columna para todos.

Esquema flexible

Cada documento lleva solo sus campos. Todos viven en la misma colección.

Equipo 5 · MongoDB03
Imaginen la tabla productos de una tienda en MySQL. Una playera tiene talla, una lámpara tiene voltaje, un libro tiene páginas. [AVANZAR] En una tabla todas las columnas existen para todas las filas: la playera carga un voltaje NULL y la lámpara unas páginas NULL. Seis de quince celdas vacías. Con tres productos no pasa nada; con doscientos tipos, la tabla se llena de columnas vacías o terminamos con una tabla por tipo. [AVANZAR] MongoDB lo resuelve guardando cada producto como un documento, parecido a un JSON. Cada documento trae solo sus campos y todos viven en la misma colección. Eso es exactamente lo que dice la actividad: cuando las filas de MySQL no son la forma natural de los datos.
01 · La regla para modelar

Lo que se consulta junto, se guarda junto.

— MongoDB Docs, Data Modeling (traducción del equipo)

Embeber

Si siempre se leen juntos, el departamento va dentro del empleado. Una consulta, sin JOIN.

empleado
departamento: { … }

Referenciar

Lo que crece sin límite va aparte: el producto guarda sus 5 reseñas recientes y el resto vive en otra colección.

producto
5 recientes
reseñas · otra colección
Equipo 5 · MongoDB04
La documentación oficial resume cómo modelar en una frase: lo que se consulta junto, se guarda junto. Hay dos herramientas. Embeber: si siempre leo al empleado con su departamento, meto el departamento dentro del empleado y llega en una sola consulta, sin JOIN. [AVANZAR] Referenciar: si algo crece sin límite, como las reseñas de un producto, guardo solo las cinco más recientes adentro y el resto vive en otra colección. Con esto le paso a Joaquín, que nos va a mostrar con qué piezas se trabaja.

Equipo 5 · MongoDB05
Gracias. Son cuatro piezas. El cliente es nuestra API en Node.js, la que recibe las peticiones HTTP. El driver es la librería oficial; se instala con npm install mongodb y traduce nuestro código en operaciones sobre la base. El servidor puede ser MongoDB Atlas en la nube o un contenedor local; adentro hay una jerarquía: una base, como tienda; colecciones, como productos; y documentos. [AVANZAR] Y la cuarta pieza: el archivo .env, que guarda la cadena de conexión fuera del código, igual que hacíamos con las credenciales de MySQL.

Equipo 5 · MongoDB06
Para usarlo con Atlas son cinco pasos. Uno: crear un cluster gratuito. Dos: crear un usuario de base de datos con su contraseña. Tres: copiar la cadena de conexión y reemplazar db_password. Cuatro: instalar el driver con npm. Y cinco: crear el MongoClient; a partir de ahí ya podemos insertar, consultar, modificar y borrar. El único requisito del driver es Node 16.20.1 o superior. Si no quieren nube, los pasos uno a tres se cambian por un contenedor de Docker, que es lo que vamos a usar en la demo.

Equipo 5 · MongoDB07
Para que no suene a idioma nuevo, aquí está el diccionario. Una tabla es una colección, una fila es un documento, una columna es un campo. El WHERE precio menor o igual a 350 se escribe como un objeto con el operador $lte. [AVANZAR] Y lo más distinto: donde en MySQL hacíamos JOIN, aquí normalmente embebemos, y si de verdad hace falta existe $lookup. Y no hay ALTER TABLE: un $set agrega el campo solo en el documento que lo necesita. Jesús les va a mostrar esto funcionando.
03 · Ejemplo

Una API de productos

  demo/server.js
import { MongoClient } from 'mongodb';
const client = new MongoClient(process.env.MONGO_URI);
const productos = client.db('tienda')
  .collection('productos');
 
app.get('/productos/:sku', async (req, res) => {
  const p = await productos.findOne({ sku: req.params.sku });
  p ? res.json(p) : res.sendStatus(404);
});
200 GET /productos/PLY-01
{ "sku": "PLY-01", "nombre": "Playera", "precio": 199, "talla": "M" }
  1. 1La cadena de conexión sale del .env.
  2. 2Base y colección; se crean con el primer insert.
  3. 3El filtro es un objeto, no SQL concatenado.
  4. 4El documento ya es JSON: sale tal cual.
Equipo 5 · MongoDB08
Este es un endpoint de nuestra API de productos; es el mismo código de la demo. [AVANZAR] Primero, la cadena de conexión sale del .env, nunca escrita en el código. [AVANZAR] Segundo, elegimos la base tienda y la colección productos; si no existen, MongoDB las crea con el primer insert. [AVANZAR] Tercero, findOne busca por sku. El filtro es un objeto, no un texto de SQL, así que no armamos consultas concatenando strings. [AVANZAR] Y cuarto, el documento ya es JSON: lo devolvemos tal cual, sin mapear filas a objetos.

04 · Frente a lo que ya vimos

Compite con uno, se combina con tres

Compite

MySQL

Los dos guardan y consultan. MySQL fija tablas y une con JOIN; MongoDB guarda documentos y embebe.

Se combina

Docker

Docker ejecuta, MongoDB guarda. En la demo, Mongo corría en un contenedor.

Se combina

GraphQL

GraphQL define el contrato de la API; el resolver hace el findOne.

Se combina

Token y permisos

Dos candados: la API valida el token; MongoDB exige su propio usuario con permisos por base.

Equipo 5 · MongoDB10
Gracias. Frente a lo que ya vimos en el curso: con MySQL compite; los dos guardan y consultan, pero uno usa tablas y JOIN y el otro documentos. Con los otros tres se combina. Docker ejecuta y MongoDB guarda: justo en la demo Mongo corría en un contenedor. GraphQL define el contrato de la API, y el resolver es el que hace el findOne. Y con el token son dos candados: la API valida el token del usuario, y MongoDB pide su propio usuario y contraseña, con permisos por base.
04 · Ventajas y límites

Qué gana

Flexibilidad
El modelo cambia con la app, sin rehacer tablas.
Menos JOINs
Lo que se lee junto llega en una consulta.
Nube gestionada
Atlas aloja el servidor; la API solo necesita la cadena.

Qué cuesta

Diseño previo
Se modela según cómo la app lee los datos.
Disciplina
La validación es opcional: si nadie la define, nadie la exige.
Plan gratuito
Sirve para clase, no para producción.
Atlas · cluster gratuito (M0)
0.5 GBalmacenamiento
100operaciones / segundo
500conexiones máximas
Equipo 5 · MongoDB11
¿Qué gana el equipo? Flexibilidad, porque el modelo cambia con la app sin rehacer tablas; menos JOINs, porque lo que se lee junto llega en una consulta; y un servidor administrado en Atlas. [AVANZAR] ¿Qué cuesta? Hay que diseñar pensando en cómo la app lee los datos; la validación es opcional, así que si nadie la define, nadie la exige; [AVANZAR] y el plan gratuito tiene límites: medio gigabyte, cien operaciones por segundo y quinientas conexiones. Para clase sobra; para producción no.
04 · Cuándo no conviene

¿Documentos o tablas?

Conviene MongoDBMejor relacional

Catálogos

Productos con atributos distintos por tipo.

Datos que cambian de forma

Perfiles, preferencias, registros de eventos.

Muchas relaciones

Alumnos, materias, grupos y calificaciones: JOIN en casi cada consulta.

Transacciones como núcleo

Pagos sobre muchos registros a la vez. Mongo las tiene; relacional es lo natural.

Equipo 5 · MongoDB12
¿Cuándo sí y cuándo no? Del lado izquierdo, lo que le queda natural: catálogos con atributos distintos, y datos que cambian de forma como perfiles o registros de eventos. [AVANZAR] Del lado derecho, mejor una base relacional: cuando los datos son muy relacionales, como inscripciones que ligan alumnos, materias, grupos y calificaciones; y cuando el corazón del sistema son transacciones sobre muchos registros, como pagos. MongoDB sí tiene transacciones, pero si son el centro del sistema, lo natural es relacional.
